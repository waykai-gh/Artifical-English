# Эксплуатация и мониторинг

## Состав production

- `bot` — Node.js 22, grammY long polling, обработка текста и голоса.
- `db` — PostgreSQL 17 с постоянным Docker volume.
- AI — основной и резервные провайдеры, переключение выполняется внутри приложения.
- Telegram — пользовательский интерфейс и канал алертов владельцу.

Оба контейнера имеют `restart: unless-stopped`, ограничения CPU/RAM и ротацию Docker-логов. PostgreSQL опубликован только на loopback-адресе сервера. Образы Node/PostgreSQL закреплены digest. Бот работает как `node`, с read-only root, без capabilities/повышения привилегий и с ограниченным `/tmp`.

## Каналы наблюдения

1. `/admin` в Telegram: пользователи, активность, AI-запросы, задержка, ошибки, токены и заполнение дневного бюджета.
2. Telegram-алерты: постоянные ошибки провайдера и полный AI outage сразу; повторяющиеся временные ошибки — после порога; одинаковые уведомления подавляются на время cooldown.
3. Docker: состояние контейнеров, health PostgreSQL и bot, restart count и JSON-логи. `/live` внутри bot проверяет запрос к БД, работающий runner и свежие успешные getUpdates; при обратном давлении учитывает завершение обработки. `/ready` дополнительно учитывает известные отказы AI/голоса/очистки/резервных копий. HTTP доступен только на loopback внутри контейнера.
4. Codex heartbeat: каждые 15 минут проверяет production через SSH как codex. При норме не пишет. Может перезапустить неисправный контейнер или повторно применить уже выпущенную ревизию из журнала деплоев. Новую версию из origin/main автоматически не публикует и не вмешивается в незавершённый выпуск другой задачи.
5. Внешний dead-man: необязательный `HEALTHCHECK_PING_URL`. Это единственный канал из перечисленных, который продолжит обнаруживать полное исчезновение сервера, когда приложение уже не может отправить алерт.

Codex heartbeat не является облачным дежурным: он зависит от включённого локального компьютера, приложения Codex и сохранённого SSH-доступа. Он не читает Telegram-входящие, а независимо проверяет те же признаки сбоя на сервере.

## Что считается инцидентом

- приложение остановлено или циклически перезапускается;
- PostgreSQL unhealthy/недоступен;
- все AI-провайдеры недоступны;
- постоянная ошибка ключа, модели или биллинга;
- устойчивый рост внутренних ошибок;
- неуспешный production-деплой или откат;
- потеря, повреждение или несанкционированное раскрытие данных.

Единичный сетевой тайм-аут при рабочем fallback не считается инцидентом. Он становится деградацией после достижения настроенного порога.

## Допустимое автоматическое восстановление

- повторная проверка, чтобы исключить кратковременный сбой;
- перезапуск только неисправного контейнера;
- `docker compose --env-file deploy/compose.env up -d --build --remove-orphans` только для уже опубликованной проверенной ревизии из журнала, при чистом checkout;
- проверка состояния, restart count и последних логов после вмешательства.

Автоматически запрещено удалять volume/таблицы/пользовательские данные, открывать БД наружу, менять секреты, тарифы, модели или продуктовые правила. Такие действия требуют владельца.

## Выпуск версии

1. Обновить код и тесты.
2. Обновить `CHANGELOG.md`; при изменении общей картины — `docs/STATUS.md`.
3. Синхронно изменить версию в `package.json` и `package-lock.json`.
4. Выполнить `npm run check`, dependency audit, Gitleaks, интеграцию с настоящей PostgreSQL, проверку Compose и контейнерный audio smoke. Эти проверки включены в `.github/workflows/ci.yaml`.
5. Создать коммит и отправить `main` в `origin`.
6. До изменения БД создать зашифрованную копию и проверить восстановление. На сервере как codex выполнить fast-forward pull, `node scripts/prepare-production.mjs` (при отсутствии Node — через закреплённый Node Docker image с bind каталога и UID codex), затем `docker compose --env-file deploy/compose.env up -d --build --remove-orphans`. Не выводить сгенерированную конфигурацию с секретами. Менять пароль существующей базы автоматически запрещено.
7. Проверить revision, `docker compose ps`, health БД, restart count и свежие логи.
8. Записать фактический результат в `docs/DEPLOYMENTS.md`. При сбое также заполнить `docs/INCIDENTS.md`.

## Первичная диагностика

```text
git rev-parse --short HEAD
docker compose --env-file deploy/compose.env ps
docker compose --env-file deploy/compose.env logs --since 20m --no-color bot
docker inspect -f '{{.RestartCount}} {{.State.Status}}' english-with-ai-bot-bot-1
docker compose --env-file deploy/compose.env exec -T db pg_isready -U english -d english
```

Команды выполняются в каталоге production-проекта. Секреты и полный `.env` в вывод диагностики не включаются.

## Резервные копии и восстановление

`scripts/install-ops.sh` запускается как codex, сохраняет чужие задания cron и устанавливает ежедневный backup в 03:17, еженедельную проверку восстановления в воскресенье 03:47 и watchdog каждые две минуты. Время — часовой пояс сервера, на текущем сервере проверяется UTC. Ключ AES-256 создаётся только при отсутствии и хранится отдельно от архивов в `~/.config/english-bot/backup.key`, права 600. Архивы `pg_dump -Fc` шифруются потоком GPG; открытый dump на диске не создаётся. Каталог `backups/` закрыт правами 700 и исключён из Git/образа.

После установки выполнить `bash scripts/backup.sh`, затем `bash scripts/scheduled-restore.sh`. Проверка сверяет SHA-256, расшифровывает и восстанавливает в новую временную БД, проверяет основные таблицы и удаляет только созданную тестовую БД. Рабочая база не перезаписывается. Бот читает только два timestamp-файла из read-only `deploy/backup-status`; архивы и ключ ему недоступны. Копия старше 26 часов или проверка восстановления старше 8 дней вызывает алерт и выключает успешные внешние heartbeat. Watchdog реагирует только на Docker unhealthy и перезапускает bot не чаще раза за 15 минут; отказы внешнего AI при исправном polling не вызывают перезапуски.

Нужны защищённые копии архива, ключа GPG, `deploy/security_key` и конфигурации вне сервера. Локальная рабочая станция может хранить аварийную копию, но не заменяет регулярную доставку в независимое хранилище. Срок хранения и автоматическое удаление архивов пока не установлены; архивы не удаляются автоматически. Решение по сроку, квоте хранилища и отражению `/forget` после восстановления обязательно до широкого запуска.

Целевой RPO для локальных ежедневных копий — до 24 часов при исправных заданиях. Это не гарантирует RPO при потере сервера: там важна последняя внешняя копия. RTO полного восстановления VPS ещё не измерен; тест restore измеряет только восстановление маленькой базы. Для аварийного восстановления сначала развернуть отдельный экземпляр БД, проверить архив и таблицы, сохранить HMAC-ключ, применить миграции/очистку, учесть удаления после снимка и лишь затем переключить бот. Не восстанавливать поверх живой базы автоматически. Откат приложения выполняется на известный предыдущий образ; добавленные таблицы совместимы, данные не удаляются.

## Границы защиты

Общие лимиты резервируются атомарно в PostgreSQL перед дорогой обработкой, выдерживают параллельные запросы и сохраняются после удаления профиля. HMAC-ключ нельзя менять при обычном выпуске. Лимиты считают обращения к боту, не стоимость токенов и не все попытки fallback. Аудит поддержки хранит HMAC действующего лица/цели, действие и время; чтение запрещено, если запись аудита не удалась. Это журнал в той же БД, без независимой защиты от изменения администратором сервера.

AI/голосовая готовность основана на последних реальных запросах; постоянные синтетические обращения к провайдерам не выполняются. Внешний heartbeat посылается только при readiness=true, но независимый сервис и его уведомления нужно настроить отдельно. Telegram-алерт из самого бота не обнаружит отключение всего VPS.

## Правило закрытия

Инцидент закрывается только после повторной проверки пользовательского пути или эквивалентной технической проверки. Перезапуск без проверки не считается исправлением. Причина, влияние, действия и оставшийся риск фиксируются в `INCIDENTS.md`.
